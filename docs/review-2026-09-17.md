# GameLibrary 代码与产品审查（2026-09-17）

## 结论与证据边界

当前是**功能较多的内部测试版**，还不是可向普通用户承诺“任意 Windows 游戏均能自动识别、导入和启动”的正式版本。宿主、数据库、扫描候选、审核、资料、启动 Profile、CLI/MCP 契约和隔离测试已成形。本轮已补通手动添加目录/EXE/SWF/LNK、移除游戏但不删除文件，以及两种数据目录下的 Desktop 单实例；它们覆盖了自动检测失败时的兜底路径，但仍需更完整的引导、发布和兼容性验收。代码声明已实现 **89/129** 个操作（`docs/coverage.md`）；此比例是接口覆盖率，不等于用户功能完成率。

本次以现有脏工作树为基线审查，保留其他 agent 的未提交改动；未连接 `LocalData/`。最新 R11 门禁见 `artifacts/build-reports/2026-09-17-r11-*.txt`：Release 构建 0 警告、0 错误；format 通过；解决方案 **414/414** 测试通过（139 单元、43 契约、8 架构、209 集成、15 无界面 E2E）。UIA 已测试真实桌面双启、首次指南、字体设置，以及系统文件选择器选 EXE→授权→入库→启动测试桩→移除且原 EXE 保留。Windows 文件选择器初次打开曾恢复到系统上次使用的 F 盘目录，测试未选择或扫描其中的文件；现为新增文件/目录选择器指定 Documents 起点，后续测试只选择 `artifacts/test-runs/<guid>/data` 内样本。历史 `docs/progress.md` 的 R6“412/412”与现在的计数无关，应以当前 TRX 为准。

审查分数是主观的产品/工程成熟度判断，不是自动化测试覆盖率：架构基础 **7/10**、核心功能闭环 **6/10**、桌面易用性 **6/10**、发布就绪度 **3/10**。保留既有 HostClient 单入口与数据安全边界；优先补齐可用性与分发验证，而非再堆接口数量。

## 架构现状

主路径为 Desktop / CLI / MCP → HostClient（命名管道）→ Host 的 `PipeServer` / `OperationDispatcher` → Infrastructure / Domain。三入口共用宿主是正确方向；库状态、扫描与启动在宿主集中，避免各入口直接操作 SQLite。宿主按数据目录单写、会话纪元与幂等键作并发/恢复防护，已有集成测试。这些是目前最值得保留的基础。

但 `src/GameLibrary.Application/` 只有项目文件，业务用例仍主要在 Host `OperationDispatcher` 的 partial 类中。按域拆文件降低了单文件长度，却没有形成 Application 用例边界；Host 同时处理协议解析、权限/修订、业务编排、数据库读写与响应 DTO。建议按“手动添加游戏 → 启动配置 → 库查询”这些纵切逐步抽取 handler/service 与接口，不宜一次性大重写。现在新增 `games.create/remove` 仍落在这个过渡结构里，债务没有因此消失。

## 关键发现与改进优先级

### P0：发布闭环与真实用户任务

- 手动添加已通过 Host 的 `games.create`，并映射 CLI/MCP；EXE、目录和 LNK 在隔离集成测试中可入库。LNK 目标、参数、工作目录经 `LnkResolver` 与 `WindowsCommandLine` 处理；失效、越界、Shell 命令不自动执行。`games.remove` 软移除且登记忽略规则，绝不删原游戏文件。**但**“自动扫描任意游戏”“所有启动器快捷方式都可直接启动”仍不是事实：某些目标是脚本、平台 URI、目录或需要外部工具，必须引导手动配置/说明不支持，而不能宣传为全面自动兼容。
- 桌面手动添加现在可选文件或目录，若不在已授权游戏文件夹内会先确认授权该范围；创建 EXE/LNK 后建议启动 Profile。R10 已用真实 UIA + 隔离测试 EXE 覆盖“选择文件→授权→入库→启动→移除不删文件”。尚未覆盖目录/LNK 的完整 GUI 点击、重启持久化、错误恢复与干净 Windows 机器验收。发布前必须完成这些剩余项；避免“源码有功能、用户包不可用”。
- 旧的 `artifacts/dist/GameLibrary-win-x64-v1.0.0.zip` 不能代表此次源码。当前另生成**不覆盖旧包**的 `GameLibrary-win-x64-r9-20260917-preview.zip`（自包含四组件；包内 CLI/Host 用隔离库验证建库、字体设置和停机）。但包内 Desktop 尚未在无 SDK 的干净机器上双击验证；托盘、升级/卸载和数据保留仍没有发布证据，故只能标“预览”。R8 预览包也不含最新的字体与指南改动。

### P1：数据一致性、性能与发布质量

- 原设置对话框遇 RevisionConflict 自动拿最新修订重放**整个旧表单**，可能覆盖其他入口刚写入的主题/周期等。本轮改为显式提示重新打开确认，不再静默覆盖；下一步可做逐字段 patch 与冲突合并。
- 原扫描“取消”只发给当前 job，完成后仍可能扫描下一轮/下一根；本轮加入批次取消状态并停止后续根。需要用可控慢扫描 fixture 补一条 UI/编排回归，而不是只靠静态审查。
- 原游戏列表固定只读前 500，收藏视图也只在这 500 项里做本地过滤。本轮加服务端收藏/标签过滤及“加载更多”；但 `GameDto` 每项分别读字段、资产、标签，仍存在 N+1 查询。现有 5000 游戏性能测试主要验证 `QueryGames`，不能证明完整 IPC DTO/桌面渲染延迟。建议批量 DTO 查询 + ItemsSource/DataTemplate 虚拟化，测 500/5000/20000 游戏。
- `games.create` 建卡与用户标题分层目前是连续两个数据库事务：极端故障下可能留下一张已建卡但标题来源未更新的卡。建议把插入及初始字段层写入做成单个仓储事务；同时给 EXE/工作目录的重解析点与配置变更补执行时复核，以免导入时的安全判断成为唯一防线。
- `OperationSchemas` 曾和宿主真实字段漂移（`profiles.create` 的 `exe/arg` 与 `games.relink` 的 `newRootPath`）。本轮修正并加 12 个定向契约测试，但还未对所有 89 个操作做机器生成/全字段一致性校验；建议将参数解析和 Schema 改为同一声明源。
- R9 发现 `settings.update` 的 CLI/MCP 会把未指定字段也作为 null 发给 Host，导致单字段修改被拒绝；已改为只发送用户实际指定的 patch 字段，并补真实 CLI 与 MCP 集成测试。多字段校验全部通过后才写 Windows 开机启动快捷方式，避免无效字体值留下系统副作用。
- 本轮还发现 `games.create/remove` 虽已加入 CLI 参数解析和请求生成，`Program.Main` 路由却漏列它们，真实命令会落入“未实现”。已修路由并新增真实 CLI 进程 → 宿主 → SQLite 的 E2E；这说明只做“CLI 可解析 + MCP 方法存在”的覆盖门禁仍不足，今后新增操作至少应补一条可执行端到端断言。
- 旧版 `artifacts/tools/package_release.py` 会覆盖现有同版本 ZIP，生成的 `uninstall.cmd` 按进程名强杀所有 Host/Desktop/MCP、再递归删除程序目录，可能波及并行隔离库。此次没有运行它，改用独立预览目录/ZIP且不包含该卸载器。正式发布前应重写为显式安装清单、按安装实例精确停机/卸载，并提供数据保留确认和可回滚路径。

### P2：结构、可访问性与安全语义

- `OperationDispatcher` partial 拆分是过渡，不是 Application 层落地。优先将输入校验、用例事务和 DTO 投影解耦；三入口继续只调用 HostClient。
- `MainWindow` 仍以 code-behind 动态创建大量控件并直接清空/重建列表。可先引入 ViewModel + `ObservableCollection` 和命令，再对设置/收藏夹/审核加可测试状态机，避免同步刷新造成焦点丢失。
- 设置与指南已补原生控件标签、Automation Name、模态窗口关闭/焦点回归和字体缩放滚动布局；UIA 验证指南与设置页基础路径。其他动态对话框在键盘导航、错误区域朗读、DPI/高对比主题方面尚未系统验收。
- 命名管道 `CurrentUserOnly` 是有效的同用户边界；握手的 `Permissions` 由客户端自报，不能把它当作对同用户恶意进程的强授权机制。若需要更强本机权限隔离，须设计可信身份/同意机制；否则文档应明确其为客户端能力声明而非 OS 安全边界。
- 同一登录会话内 Desktop 已单实例，Host 仍按数据目录单写。这里刻意保留两级边界：用户双击不会多开 UI；CLI/MCP 对不同隔离库的测试或维护操作仍可有各自 Host。需要在帮助里解释“关闭窗口/托盘退出/停止后台”的差别，避免误以为后台进程是多开的 Desktop。

### R10 真实点击路径审计

按用户动作顺序追踪 `MainWindow.Scanning.OnManualAddClick` → Windows `OpenFileDialog` → `roots.list/add` → `games.create` → `profiles.create` → `RefreshAsync`/`RenderSidebar` → `PlayGameAsync` → `RemoveGameAsync`。测试仅复制 `GameLibrary.TestProcessStub` 到独立数据目录；从库移除后检查宿主列表为空而 EXE 仍在。

- **P1 / 添加后详情可能不可见**：旧搜索条件仍参与 `games.list` 服务端查询。用户刚添加成功却看到空列表；修复为添加成功后清除旧搜索并切回“全部游戏”，UIA 先输入不匹配搜索词再添加，验证新游戏详情和可启动按钮可见。
- **P2 / 异步刷新竞态**：添加后的 `RefreshAsync` 若被事件轮询触发的新刷新覆盖，旧代码随后在尚未更新的列表里找新 ID，一次性选中会落空。改为待选 game ID 留在窗口状态，由下一次成功渲染消费；当前 UIA 覆盖普通路径，尚未用可控事件调度器确定性重现交错。
- **P2 / 系统文件对话框测试定位**：文件列表项和“打开”按钮可能共享 AutomationId=1；回归测试同时限定 `ControlType.Button`，避免误点其他目录。选择器起点设为 Documents，降低系统上次访问目录意外干扰。此项是测试稳定性及用户起始位置改进，不应记作宿主入库逻辑缺陷。

### R11–R12 缓存路径与清理代码审查

本节按 `code-reviewer` 的安全、性能、可维护性维度单独评价缓存子系统；以下评分不是整个项目的质量分。该范围目前 **8/10**：清理边界、自定义位置、所有权标记和实际预览写入已完成；容量策略与强对抗并发替换仍待补。

| 严重度 | 位置/代码段 | 证据与修复建议 |
|---|---|---|
| High（已修） | `OperationDispatcher.Observability.cs` 的 `CacheRebuild` 原先 `Directory.EnumerateFiles(..., AllDirectories)` | 没有显式禁止目录链接/junction，可能越过 `data/cache` 的预期边界。现改为 `CacheDirectoryCleaner` 逐层检查并跳过重解析点；缓存根本身是链接时拒绝清理。隔离集成测试验证链接目标文件仍在。自定义位置只清理带本库所有权标记的 `GameLibraryCache/<库摘要>/previews`，标记与父目录文件保留。 |
| Medium（已修） | `MainWindow.Settings.cs`、`SettingsStore.cs`、`AssetsGet` | Desktop 通过系统目录选择器保存缓存父目录；Host 创建带库身份标记的专属子目录并生成最大 720 像素、1 MiB 的 PNG 预览。设置已同步 CLI/MCP/schema；切换位置不移动或删除原图/旧缓存，reset 回默认。真实 Host、CLI、MCP 与 UIA 均有回归测试。 |
| Medium（剩余） | `CacheDirectoryCleaner.Clear` 属性检查与 `File.Delete` 之间 | 防链接检查不是抗同用户恶意进程的原子句柄约束；若外部进程在检查与遍历之间持续替换目录，仍有 TOCTOU 窗口。专属命名空间、所有权标记和逐层复核降低了误删面，但若要防同用户恶意进程，仍应改为句柄相对访问或按可信清单删除。 |
| Low（已修） | 原 `CacheRebuild` 删除统计 | 旧代码在 `File.Delete` 成功前增加 `removedBytes`，被占用文件也会计为已删除字节。现在成功删除后才统计，另返回 `skippedErrors`/`skippedLinks`，测试锁定文件场景。 |

未发现该路径涉及 SQL 注入、XSS 或硬编码密钥；主要风险是文件系统边界和功能语义。自定义缓存位置已可用，但它是可再生封面预览缓存，不是 `library.db`、用户原图或整个数据目录的迁移能力。

## 建议实施顺序与验收

1. **补齐真实桌面工作流剩余路径**：EXE 主路径已跑通；继续测目录/LNK GUI、重启后仍在、错误恢复、断链、并发修改/重试，不访问日常库。
2. **用户化 Desktop**：为数据目录设计停机迁移/校验/回退；补错误恢复指引、字体与控件密度独立调节、收藏夹拖放/排序/批量操作；缓存补容量上限/自动淘汰，并以人工 DPI/高对比检查验收。
3. **用例层/性能**：逐域抽取 Application handlers；建卡与标题写入事务化，批量读 DTO 和虚拟化列表；添加 IPC 端到端大库基准。
4. **正式 Windows 发布**：自包含包/安装器、签名、干净机器、升级/卸载与恢复演练；打包产物与源码提交一一对应。先证明发布包可用，再扩大检测器覆盖。

审查不是说现有代码不可用：当前受支持引擎、手动目录/EXE/LNK 的隔离流程有自动化覆盖，EXE 桌面点击主路径也已验证；但在上述剩余桌面路径与正式发布验收完成前，不宜把它描述为完整的通用本地游戏库。
