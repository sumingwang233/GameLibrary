# ADR-0004 SQLite 可恢复性

- 状态：已接受
- 日期：2026-09-13（T20）

## 决策

1. 唯一 Host 拥有数据库连接；每连接启用外键、WAL、busy_timeout≈5s；单写入队列，事务内不做文件枚举/解码/进程启动/联网。
2. migration 按连续整数版本、单事务执行；升级前用 SQLite 备份 API 生成一致快照（不复制运行中的 WAL 库）。
3. 损坏库进入 `RecoveryRequired` 模式：只开放 capabilities/diagnostics/backups，不重建空库、不启动扫描。
4. 恢复控制收据与维护日志存放在 LocalData 控制区，**不随业务库回滚**；恢复成功生成全新 `dataEpoch`，旧 Revision/游标/计划全部失效。
5. 高版本库被旧程序打开时拒绝写入，不自动降级。

## 理由

多进程写 SQLite 会产生锁竞争与半写状态；恢复时控制收据若随库回滚，重试会再次覆盖、找不到原请求。dataEpoch 是防止“旧状态复活”的一致性屏障。

## 被排除方案

- 多入口各自开连接：违背唯一 DB 所有者，也破坏事务/权限统一。
- 迁移失败后直接用旧备份覆盖 WAL 库：可能撕裂事务。
- 恢复时沿用旧 epoch：客户端缓存与游标会操作已被回滚的状态。

## 不可变约束

- 备份 manifest 含 schema/应用版本、libraryInstanceId、业务配置、用户图片清单、逐文件 SHA-256；缓存与外部游戏不在备份内。
- 恢复先备份当前状态、进入维护模式拒绝新写、暂存验证后切换，全程由维护日志记录。

## 迁移影响

备份 schema 演进需保留版本化导入；恢复保留 libraryInstanceId 仅记录 provenance。

## 验证用例

DB-03/04、REC-01/02、AI-10（旧游标/旧计划被拒）。
