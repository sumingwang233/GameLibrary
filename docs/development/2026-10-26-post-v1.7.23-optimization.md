# v1.7.23 之后的代码与前端优化（第一至四轮）

2026-10-26。依据「k3.1 审查方案」的优先级，在合并 `origin/main`（v1.7.23）后的本地分支 `codex/optimize-v1.7.23` 上完成第一轮优化：连接与作业可靠性、分页与状态一致性、前端可访问性与动效。第二轮接着处理方案第 5 阶段的安全项与性能候选：Tauri 权限收紧、`GameBatchBar` 的批量 IPC，以及对 `assetCache` 与 SQL 索引的实测判断。第三轮把第一方客户端的握手权限从“不声明即不限权”改成显式声明，并在真实通道上验证权限确实生效。第四轮把剩下两件需要“先量后改”的事查清：CSP 是否可以直接启用、授权默认拒绝的破坏面有多大、列表查询在 5000 游戏规模下的真实延迟。四轮都未登记新版本号，未打包、未推送、未发布；工作区里用户对安装器与网站的改动保持原样。

## 范围与约束

- 不引入 Redux、路由、WebSocket，不重写 Host；沿用 `App.tsx` 作为组合根与既有 hooks。
- `games.list` 只做 additive 契约扩展，`limit` 缺省或 `<=0`（全量）行为不变，旧客户端无需修改。
- 不改数据库 schema，不新增第三方依赖；既有 operation、API 版本保持兼容。
- 只修改与方案相关的最小代码面；工作区里用户删除的安装器脚本、`website/next-env.d.ts` 等未跟踪/删除项不纳入提交。

## 问题与结果

| 方案项 | 原因与修复后的行为 | 主要文件 |
|---|---|---|
| P1 连接失效后永久握手失败 | Host 断开后 `HostConnection.InvokeOnceAsync` 会清空管道与握手，重建失败时异常向上抛出；`BridgeServer` 仍缓存这个连接对象，之后每个请求先读 `Handshake` 属性，直接抛「尚未完成握手」，而不是重连。现在 `EnsureConnectedAsync` 在空连接时先按缺口重建握手，重建失败才抛 `HostClientException(HostUnavailable)`；`BridgeServer` 在调用前确保连接可用，失败后丢弃缓存，停机时也清掉缓存连接。 | `HostConnection.cs`、`BridgeServer.cs` |
| P1 轮询无永久失败处理 | 扫描和标题翻译原来只在成功响应里更新状态：NotFound、管道断开等异常被吞成 `null` 或一条提示，循环继续每 500–700ms 空转，作业已经消失也停不下来。新增 `useJobPolling`，用连续失败预算终止轮询并给出可读原因；NotFound 立即结束；成功一次即清零失败计数。 | `useJobPolling.ts`、`useScanJobs.ts`、`useTitleTranslation.ts` |
| P1 分页游标错位 | 服务端按原始行做 `LIMIT/OFFSET`，前端却拿「合并去重后的本地数组长度」当下一页 offset；标题翻译等改动让某行更新后重新落位，重复行会让 offset 偏小，反复抓同一段甚至提前停止。`games.list` 增加 `nextOffset`/`hasMore`（`limit<=0` 时为 `null`/`false`），前端按游标推进，旧响应与本地回退路径保留。 | `GamesHandler.cs`、`useGamesQuery.ts`、`contracts/operations.v1.json` |
| 详情保存旧快照 | 选中项存整个 `GameItem`，后台 reload 或标题补丁之后详情继续显示打开瞬间的标题、收藏、封面。改为 `selectedGameId` 加列表外回退快照，渲染时优先取当前列表里的同 id 对象；相似建议跳转、`launch.exited` 等列表外路径仍可用。 | `App.tsx`、`selection.ts` |
| 审核部分失败清空选择 | `useCandidateReview` 把失败聚合成一个异常，`ReviewList` 等不到成功返回就清空全部勾选，失败项要重新找。现在批量结果按 `candidateId` 对齐，返回成功项与失败摘要；`ReviewList` 只清除成功项，整批异常时保留勾选，错误交给 `actionError` 呈现。 | `useCandidateReview.ts`、`ReviewList.tsx`、`App.tsx` |
| Unity 对话框提交串扰 | 单个 `submitting` ref 同时服务所有游戏，切换游戏后旧请求的失败会被标到新行。改为按 `gameId` 记录提交目标，状态合并只更新对应游戏，关闭对话框不丢其他游戏的进行中状态。 | `UnityTranslationDialog.tsx` |
| 幂等键复用 | 幂等键原来只按 `intent` 缓存，同一 intent 换参数会复用旧键，把新请求当成重放。现在键绑定参数指纹（稳定序列化），参数不同即生成新键；键仍由 `acquireKey/releaseKey` 管理生命周期。 | `api.ts` |
| 徽章对比度不足 | 11px 文本配 `bg-steam-soft` 在暗色约 3.32:1、浅色约 4.31:1。改用更深的文字色后，默认徽章暗色约 6.49:1、浅色约 11.74:1；steam 为 8.63:1/4.63:1；favorite、danger、success 的 `text-primary` 为 7.99–8.78:1（暗）与 12.83–13.33:1（浅）。 | `badge.tsx`、`index.css` |
| Sheet 标题关联失效 | Radix 的 `aria-labelledby` 指向自定义 `titleId`，但 `asChild` 的 `h2` 从未挂上这个 id。现在标题与描述都显式绑定同一组 id，屏幕阅读器能读出标题；同时补 160–200ms 进出场动画，`reduced-motion` 下关闭。 | `sheet.tsx`、`index.css` |
| 卡片嵌套交互元素 | `article role="button"` 里塞了 checkbox 和启动按钮，键盘与读屏语义冲突。改为普通容器加一张覆盖整卡的按钮，checkbox 与启动按钮作为兄弟节点叠在上层，整卡 hover 抬升保留。 | `GameCard.tsx` |
| 扫描 live region 过大 | `role="status"` 覆盖了每秒更新的耗时和取消按钮。现在只有状态标题进入 live region，计时器与按钮移出并标记 `aria-hidden`。 | `ScanProgressBar.tsx` |
| 骨架屏动效 | `animate-pulse` 常驻，改为 `motion-safe:animate-pulse`，由组件自己表达减少动态的意图。 | `skeleton.tsx` |

## 契约与兼容

- `games.list` 的响应新增 `nextOffset`（`number | null`）与 `hasMore`（`boolean`），是增量字段；旧客户端继续用 `total`/`items` 不受影响。`limit` 缺省或 `<=0` 时两个字段恒为 `null`/`false`。

- 未新增数据库迁移、依赖或配置项；`global.json`、`Directory.Build.props` 未改。

## 第二轮：批量 IPC 与权限收紧

| 方案项 | 原因与修复后的行为 | 主要文件 |
|---|---|---|
| 批量操作逐项 IPC | `GameBatchBar` 原来对每个勾选的游戏先 `games.get` 拿最新 revision，再发一次变更，N 项约 2N 次 IPC，部分失败时前面的结果已经生效。现在收藏、取消、加标签、移除各走一次批量操作（`games.update_batch`、`tags.assign_batch`、`games.remove_batch`），单批上限 1000、前端按 500 分块顺序提交，回执逐项对齐 `gameId`；失败项汇总成文案，刷新后可直接重试。 | `GameBatchBar.tsx`、`BatchRequests.cs`、`SqliteLibraryStore.Batches.cs`、`GamesHandler.cs`、`TagsHandler.cs` |
| 全局注入与插件权限面过大 | `withGlobalTauri=true` 把整套 Tauri API 挂到 `window.__TAURI__`；`opener:default`、`dialog:default` 放开的是整套默认权限，其中 reveal-item、打开路径、保存对话框、消息框都没用到。关闭全局注入（前端本来就用静态导入，`__TAURI__` 只是非 Tauri 环境的兜底），权限改成 `opener:allow-open-url`、`opener:allow-default-urls`（http/https/mailto/tel 作用域）与 `dialog:allow-open` 三项。 | `tauri.conf.json`、`capabilities/default.json` |
| 默认不限权的授权模型 | `HasPermission` 对 `GrantedPermissions=null` 直接放行，是有意的第一方默认；改成默认拒绝会让本机 CLI、MCP 与桌面端所有调用一起失效。本轮只把它写进记录，不改变语义。 | `OperationDispatcher.cs:414-422` |
| CSP 仍为 null | 需要先确认真实窗口里 asset 协议、内嵌字体与远程 URL 的加载方式，没有运行环境就不改。 | `tauri.conf.json` |
| 旧 Unity 密钥文件 | 设置里保存新密钥时不会清理旧 credential 文件；属于清理型改动，要先确认没有引用，留待后续。 | `UnityTranslationSettings.cs` |
| SQL 索引与 assetCache | 核对 `games.list` 的筛选/排序 SQL 与现有索引：active、updated、title 等已有索引，标题排序用相关子查询取显示名，普通索引覆盖不了；`assetCache` 已有 64MiB 预算、LRU 与测试覆盖。两项都判定“先实测再改”，本轮不改 SQL 与缓存实现。 | `LibraryCatalogStore.Games.cs`、`assetCache.ts` |

## 契约与兼容（第二轮）

- 三个批量操作由 `scripts/generate_operations.py` 统一生成到契约、CLI 命令表与 MCP 工具，目录从 151 项增至 154 项；CLI 为 `games update-batch`、`tags assign-batch`、`games remove-batch`，MCP 工具为 `games_update_batch`、`tags_assign_batch`、`games_remove_batch`。
- 回执是逐项语义：Envelope 仍 `ok=true`，`data.items[{gameId, ok, revision?, errorCode?, message?}]` 加 `updated`/`failed` 计数；只有整批参数非法（items 非数组、为空、超限、重复 `gameId`、单条缺字段）才返回 `InvalidArgument` 并整批回滚。单项业务失败只回滚该项，其余继续提交；单项数据库异常记为 `InternalError`，同样不阻断其他项。这与 `candidates.review_batch` 的既有语义一致。
- `games.remove_batch` 只把记录置为已移除并登记 `ExactPath` 忽略规则，不删除磁盘文件；`tags.assign_batch` 对已挂同一标签的项算成功但不 bump 游戏 revision。
- 前端不再回查 revision，`expectedRevision` 直接取列表项；冲突项会出现在失败列表里，列表刷新后可以重试。幂等键仍由 `api.operation` 的参数指纹生成，三个操作都要求幂等键，收据与整批事务同事务落库。

## 第四轮：CSP 与授权策略评估、性能实测

这三项都不适合在没有量测的情况下改实现，本轮的做法是：能查清的查清并留下证据，需要真实运行环境才能结论的写进验收清单，不硬上。

| --- | --- | --- |
| CSP | 前端没有远程脚本、样式或字体；唯一的远程来源是 `update.ts:42` 对 `https://api.github.com/.../releases/latest` 的 `fetch`。封面经 `assets.get` 以 base64 `data:` URL 显示；没有 `dangerouslySetInnerHTML`、`eval`、`new Function`。`withGlobalTauri` 已在前一轮关闭。 | 可以写出很紧的 CSP，但只在真实 WebView 里生效，仓库里没有能在 CI 验证它的手段；先给草案与验收步骤，不直接启用。 |

```text
object-src 'none'; base-uri 'none'; frame-ancestors 'none'
```

`style-src` 保留 `'unsafe-inline'` 是因为 Radix 等组件会写内联样式，去掉会样式错乱；`connect-src` 的 `ipc:` 与 `http://ipc.localhost` 是 Tauri v2 在 Windows 上的 IPC 通道；`https://api.github.com` 只给更新检查用。验收步骤：写入 → `cargo build` → 启动打包后的程序 → 依次确认窗口渲染、封面显示、更新检查、详情滚动与对话框动画；控制台报什么缺什么，按上面的允许清单补，缺一项表现为白屏或样式丢失。`cargo check` 只校验权限标识，不校验 CSP，别拿它当验收。

性能实测（本机 Release 构建，`dotnet test --no-build --filter GameCatalogPerformanceTests`，4/4 通过，1.14 秒）：

- `T26_PagedQuery`：5000 游戏、`title` 排序、20 页 × 100 条采样，p95 ≤ 150 ms 的预算门禁通过，整个用例 214 ms。
- `T26_SearchAndTagFilter`：搜索命中 1 条 + 100 个游戏同标签过滤 + `tags.list` 计数，三项都在 200 ms 预算内，用例 116 ms。
- `R41_BatchEnrichment`：5000 张卡的批量充实 207 ms（预算 300 ms）。
- `QueryGames_SortsByTitleUpdatedAndAcceptedTime`：三种排序正确性 29 ms。

结论：迁移 19 建的活跃游戏索引、`game_fields` 与 `game_title_translations` 的主键，已经覆盖了列表查询；方案担心的“分页排序退化成全表扫描”在 5000 规模没有出现，所以不加索引、不碰 schema。唯一还可能在数万级游戏时变慢的是 `ORDER BY` 里的逐行子查询（`displayedTitle`），那需要真实大数据集才谈得上验证，本轮不造数据凑结论。这些延迟断言在 CI 上不强制（源码里 `EnforceLatencyBudget` 只在非 CI 生效），数字只代表本机。

`assetCache` 这边：单测已经覆盖 LRU 淘汰、并发合并、失效代际和超大值不入缓存，账目按 2 字节/字符保守估算，上限 64 MiB。真实 V8 堆占用不是这套账目能证明的，需要在打包程序里用内存剖析器看，归入人工验收。
