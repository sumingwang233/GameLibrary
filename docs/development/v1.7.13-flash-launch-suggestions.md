# v1.7.13 Flash 合集建议启动方式

2026-10-12。基于 v1.7.12，修复独立游戏合集审核后缺少建议启动方式；不新增数据库迁移、operation 或依赖。

## 审计与原因

- `FlashCandidateReviewService.Review` 将每个选中的合集入口录为 `kind=fileGame`、`engine=flash`，`RootPath` 与 `EntryPath` 都是该文件。入口没有在入库时丢失。
- `CandidateReviewHandler.ToEnvelope` 发布 `candidate.updated`，唤醒既有后台建议队列；合集目录本身转为 deferred，其下游戏仍由队列发现。
- `LaunchSuggestionService.DiscoverAsync` 此前把独立文件游戏转回父目录扫描，超过 256 个文件时直接跳过。
- `LaunchSuggestionDetector.Detect` 仅识别 EXE。即使是小型 SWF 合集，也无法生成 SWF 建议。目录启发式不适用于已经明确确认的独立文件身份。
- `LaunchRegistry.AddSuggestions` 已有去重、持久化和删除/废弃保护；`Execute` 已支持 SWF 的 Windows 文件关联启动，无需新播放器或启动协议。

```mermaid
flowchart LR
  A[审核合集并选择入口] --> B[每个文件独立入库]
  B --> C[candidate.updated 唤醒建议队列]
  C --> D{游戏身份}
  D -->|fileGame / manualFile| E[检查所选文件存在、类型与链接边界]
  E --> F[该文件的单入口建议]
  D -->|目录游戏| G[保留既有目录识别与预算]
  G --> H[AddSuggestions]
  F --> H
  H --> I[持久化 suggested；删除与废弃状态保留]
```

## 实施

1. `LaunchSuggestionService.cs`：独立文件身份直接用其 `RootPath` 生成建议，支持 EXE/SWF，工作目录为父目录。不枚举同目录其他游戏，不受目录文件数量上限影响。目录游戏继续使用原检测器和预算。
2. `LaunchSuggestionHostTests.cs`：通过真实扫描、公共 JSON 序列化、管道 inspect、accept/review_batch、profiles.list 验证完整链路；覆盖小型/301 文件合集、未选入口不入库、自动事件唤醒、重启补齐和删除建议不复活。
3. 同步 `Directory.Build.props`、npm package/lock 与 Cargo product/lock 到 1.7.13；更新图谱与发行记录。

复用既有 `single-entry` 评分原因，状态仍为 `automatic/suggested`，不会把目录审核当作运行成功或直接设为默认。建议成功/失败确认继续沿用既有运行观察机制。用户的手动默认方式、删除或废弃记录不被重建覆盖。

## 升级、回退与验收

启动新版会由同一队列为此前已入库的独立文件游戏补齐缺失建议，无需重新审核合集。库根必须仍注册且文件可读；缺失文件、越界或系统链接继续拒绝。SWF 使用本机已有文件关联，实际播放取决于已安装的 Flash 播放器。

没有 DDL 或数据重写；回退可安装旧版并保留数据库，新增建议仍兼容原有 Profile 格式。回退前先备份游戏库。

优先级仅处理入口建议缺失这一根因。验收标准：所选每个文件只有自身入口建议、可推荐但尚未验证；未选文件不入库；大合集不被 256 文件上限阻断；升级补齐且尊重删除抑制。真实执行和最终安装验收与隔离回归分开记录。
