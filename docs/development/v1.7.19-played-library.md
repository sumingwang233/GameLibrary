# v1.7.19 已游玩游戏库

基线：`cb80b0d`（v1.7.18），2026-10-17。本次为未发布源码，未打包或推送。

## 原因与行为

v1.7.18 已保存独立的 `games.played` 状态，但桌面列表没有传入对应筛选，侧栏也没有“已游玩”入口。因此标记后游戏仍留在主库。

主游戏库现在只显示未游玩游戏；左侧“已游玩”显示已标记的游戏。点击两个入口会清空搜索、收藏、标签和封面条件，并从第一页加载。标签、搜索、封面筛选和排序在当前游戏库内生效；点击“收藏”会返回主库并筛选未游玩的收藏。主库数量使用相同的未游玩条件。

在详情页取消已游玩标记后，游戏回到主库。成功游玩结束后的自动标记沿用 v1.7.18 实现。切换列表不改变游戏 ID、评分、收藏、入库时间、标签或封面。

## 实现与契约

```mermaid
flowchart LR
    Sidebar[侧栏：全部游戏 / 已游玩] --> Filters[App：playedOnly]
    Filters --> Query[useGamesQuery：played false / true]
    Query --> Handler[games.list：可空布尔校验]
    Handler --> Store[QueryGames：同一 WHERE 统计和分页]
    Update[详情修改 / 成功游玩标记] --> Refresh[game.updated / reload]
    Refresh --> Query
```

`games.list.played` 是可选布尔参数：`true` 仅已游玩，`false` 仅未游玩，缺省或 `null` 不限状态。桌面始终明确传值；CLI/MCP 旧调用保持原有全库语义。CLI 的 `games list --played` 和 `--unplayed` 复用已有解析字段，MCP 与 schema 从中央 catalog 生成。非布尔值返回 `InvalidArgument`。

筛选直接进入 SQL，统计和分页共用条件。切换时清空旧列表和页数；迟到的旧响应由现有 request 身份判断丢弃。使用 schema29 的已有字段，无数据库迁移、新路由、全局状态库或依赖。
