# 候选整理、原文件清理与提权启动

## 审计

- 候选按物理路径持久化；原路径被搬走后仍停在 pendingReview，查询未检查存在性。
- EXE 通过 CreateProcess 启动，遇到 Windows 错误 740 时直接失败。用户截图证明此处需要 Windows 提权，不能据此判断用户选错汉化 EXE。
- 侧栏底部的六个操作占用标签与收藏夹空间；顶部已有对应操作入口基础。

## 链路和方案

```text
进入待确认 / 每 15 秒刷新 → 检查路径 → 确认不存在 → 退回 observed 等待重新发现
扫描发现恢复路径 → observed 晋升 pendingReview
删除按钮 → 展示准确路径确认 → 边界/修订/共用/链接检查 → Windows 回收站 → 移除记录
启动 EXE → 错误 740 → ShellExecute runas → UAC 同意启动 / 取消提示
```

优先修复候选和提权，再增加回收站清理及顶部入口。无数据库迁移：沿用 observed 状态保存旧记录，不写忽略规则；磁盘离线、权限错误不判定为删除。已接受和用户忽略的记录不受影响。

## 文件与界面

- `LibraryCatalogStore` 和 `CatalogingHandler` 核对待审核路径，接受候选前再次确认存在性。
- `GamesHandler` 保留 games.remove 默认语义，显式 deleteFiles + confirmedPath 才使用回收站。文件型游戏只删除入口文件；目录型游戏删除整个目录；快捷方式拒绝原文件清理。
- `DetailSheet` 两个删除语义分开，确认框显示路径、存档及补丁范围，失败后保留错误提示。
- `TitleBar` 承接侧栏底部全部操作，设置使用主色按钮；`Sidebar` 保留导航、收藏夹和标签。App 继续使用原状态控制器，无路由迁移。
- `LaunchRegistry` 仅在 740 时重试提权，不要求整个 GameLibrary 管理员运行，不替换用户配置的 EXE。

## 验证与限制

回归包含：搬移/恢复候选、删除确认及库根保护、临时游戏回收与旁边文件保留、幂等重放、模拟 740/1223 并验证路径参数保持。未操作用户实际游戏，也未自动批准真实 UAC。

文件系统与 SQLite 不能跨系统事务提交；回收成功后数据库若失败，文件可从回收站恢复。回收失败保留库记录；Windows 可能因回收站不可用显示系统提示。删除大目录时同步操作可能较慢。普通 CLI games remove 保持不删文件；MCP 可传显式确认参数。

回滚只需回退代码，无 schema 回退；已移入回收站的文件由用户恢复。测试只回收临时测试目录。
